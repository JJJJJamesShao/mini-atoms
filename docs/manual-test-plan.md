# mini-atoms 手动测试方案

> 目标：验证面试官反馈的两个核心问题（代码生成稳定性、项目历史版本管理），
> 以及已修复的流式传输和多 Agent 执行效果。
>
> 测试环境：https://mini-atoms-five.vercel.app/
> 测试账号：reviewer@mini-atoms.demo（付费账号，无限额度）

---

## 测试环境准备

1. 打开浏览器无痕模式（避免缓存干扰）
2. 访问 https://mini-atoms-five.vercel.app/
3. 使用 reviewer@mini-atoms.demo 登录
4. 确认登录成功后看到项目列表页

## 一、新项目代码生成稳定性测试

> 对应面试官反馈："代码生成阶段长时间没有完成，无法得到新的可运行预览"
> 已修复措施：PR #29 SSE 心跳保活 + PR #26 生成阶段异步进度提示 + PR #30 流式化 + 节点级超时

### 测试 1.1：基础网页应用生成（默认 SOP）

**步骤：**

1. 在首页输入框输入："做一个待办事项列表应用，可以添加、删除、标记完成，使用本地存储保存数据"
2. 点击生成按钮
3. **观察阶段卡片流转**：
   - clarify → spec → **approve（弹出 SpecCard）** → generate → verify → done
4. 在 approve 阶段点击「确认规格」
5. **观察 generate 阶段**：
   - 应显示"正在生成代码..."的实时进度
   - 应看到每 3 秒刷新的 thinking/progress 事件（如"已生成 1200 字符..."）
   - 不应出现"页面卡住"的感知（超过 5 秒无反馈即算失败）
6. 等待完成，右侧 PreviewFrame 应显示可交互的待办应用

**预期结果：**

- ✅ generate 阶段有持续进度反馈（不卡住）
- ✅ 最终生成可运行的单文件 HTML 应用
- ✅ 阶段卡片状态正确流转，无遗漏或错误状态

### 测试 1.2：复杂全栈应用生成（多阶段 SOP）

**步骤：**

1. 输入："做一个带用户登录功能的博客系统，有文章列表、文章详情、评论功能，使用 localStorage 模拟数据库"
2. 观察 SOP 路由：应进入 `fullstack-app` 多阶段流程
3. **观察阶段卡片**：
   - clarify → spec → approve → **generate-schema → verify-schema → generate-shell → verify-shell → generate-pages → verify-pages → merge → verify → done**
4. 每个 generate-X 阶段应有独立的进度提示
5. 等待完成

**预期结果：**

- ✅ 正确路由到 `fullstack-app` SOP（版本卡片标题显示「【全栈应用】...」）
- ✅ 每个子阶段（schema/shell/pages）有独立的进度反馈
- ✅ merge 阶段显示"合并各阶段产物"
- ✅ 最终生成完整的单文件 HTML 应用

### 测试 1.3：游戏类应用生成（跳过 approve 的精简 SOP）

**步骤：**

1. 输入："做一个 2048 游戏，要有动画效果和分数统计"
2. 观察阶段卡片：
   - clarify → spec → **generate（无 approve 门）** → verify → done
3. 确认没有 approve 阶段（游戏 SOP 自动跳过）

**预期结果：**

- ✅ 直接进入 generate，不经过 approve 门
- ✅ 生成可玩的 2048 游戏

### 测试 1.4：超长生成压力测试

**步骤：**

1. 输入一个复杂需求："做一个模拟城市建设的游戏，有资源管理、建筑升级、人口系统、昼夜循环、天气系统，界面要精美"
2. 这个需求会触发多次 fix 循环（因为校验严格）
3. **观察**：
   - generate 阶段是否持续有进度反馈（即使超过 60 秒）
   - SSE 连接是否保持（心跳每 15 秒一次）
   - 如果进入 fix 循环，是否显示"第 N 轮修复重试"

**预期结果：**

- ✅ 即使生成时间超过 2 分钟，前端仍有进度更新
- ✅ 不会超时断开（心跳保活机制）
- ✅ fix 循环有明确反馈，用尽 5 次后优雅失败

## 二、项目历史版本管理测试（核心）

> 对应面试官反馈："刷新页面后，刚才的修改结果显示成了独立项目，原项目和修改后的版本没有保持在同一个项目历史中"
> 已修复措施：PR #25 对话迭代追加版本 + PR #27 流水线过程数据持久化 + PR #31 approve 挂起门持久化

### 测试 2.1：基础版本追加（同一项目内修改）

**步骤：**

1. 先完成测试 1.1，生成一个待办应用（项目 A）
2. 在工作区底部输入框输入修改需求："把背景改成深色模式"
3. 点击发送
4. 观察：
   - 版本列表应出现 **v2**，且标注"基于 v1"
   - 阶段卡片重新走一遍流程
   - 完成后右侧预览应显示深色模式的待办应用
5. **关键验证**：打开浏览器 DevTools → Application → Local Storage / IndexedDB，确认没有异常

**预期结果：**

- ✅ v2 追加到同一项目，不是独立项目
- ✅ 版本卡片显示"基于 v1"的分叉关系
- ✅ 右侧 PreviewFrame 正确显示 v2 的深色模式效果

### 测试 2.2：刷新页面后版本历史恢复

**步骤：**

1. 完成测试 2.1（项目 A 有 v1、v2）
2. **刷新页面（F5）**
3. 从 Sidebar 点击项目 A 进入
4. 观察版本列表：
   - 应显示 v1 和 v2
   - v2 应标注"基于 v1"
5. 点击 v1，右侧应显示原始浅色版本
6. 点击 v2，右侧应显示深色模式版本

**预期结果：**

- ✅ 刷新后项目 A 的版本历史完整保留
- ✅ 版本切换正常，预览正确
- ✅ 版本间的父子关系正确显示

### 测试 2.3：从旧版本分叉修改（非最新版）

**步骤：**

1. 项目 A 已有 v1（浅色）、v2（深色）
2. **选中 v1**（点击 v1 版本卡片）
3. 输入修改："添加一个筛选功能，可以按已完成/未完成筛选"
4. 点击发送
5. 观察：
   - 应生成 **v3**，标注"基于 v1"（不是基于 v2）
   - v3 应有筛选功能，但背景是浅色（继承 v1）

**预期结果：**

- ✅ 可以从任意历史版本分叉，不只是最新版
- ✅ 分叉关系正确显示（v3 基于 v1）
- ✅ 代码正确继承所选版本的上下文

### 测试 2.4：approve 阶段刷新恢复

**步骤：**

1. 首页输入："做一个计算器应用"
2. 等待走到 approve 阶段（弹出 SpecCard）
3. **在 approve 阶段刷新页面（F5）**
4. 刷新后，应从 `/api/gates/pending` 恢复挂起状态
5. 观察：
   - 应显示"规格待确认（页面刷新后恢复）"的恢复卡片
   - SpecCard 应显示之前生成的规格
6. 点击「确认规格」
7. 观察：
   - 如果原流水线仍在后台运行（同进程），应返回 "live" 并继续
   - 如果服务已重启，应返回 "recorded" 并提示"请基于当前版本重新发起"

**预期结果：**

- ✅ 刷新后恢复 approve 等待状态
- ✅ 可以正常确认或拒绝
- ✅ 确认后流水线继续执行或给出清晰提示

### 测试 2.5：generate 阶段刷新 + 轮询恢复

**步骤：**

1. 首页输入一个复杂需求（触发较长生成时间）
2. 确认 approve 后，在 generate 阶段**刷新页面**
3. 刷新后，从 Sidebar 找到刚才的项目并点击进入
4. **观察轮询行为**：
   - 前端应每 5 秒轮询 `/api/projects/{id}`
   - 当检测到新版本落库后，自动重建工作区
5. 等待后台生成完成

**预期结果：**

- ✅ 刷新后进入项目，显示"后台生成中…（完成后自动刷新）"
- ✅ 轮询检测到新版本后自动刷新
- ✅ 最终版本正确追加到原项目

## 三、追加修改流式传输测试

> 对应已修复：PR #30 LLM 调用流式化

### 测试 3.1：对话迭代的流式效果

**步骤：**

1. 已有项目，选中最新版本
2. 输入修改："把所有按钮改成圆角，添加悬停动画效果"
3. **观察 generate 阶段**：
   - 应看到"对话迭代：基于现有代码 XXXX 字符做增量修改..."
   - 流式接收 Patch 指令时应有进度更新（每 2000 字符）
   - 应看到"收到修改指令，正在解析并应用..."
   - 如果 Patch 成功，显示"增量修改完成：N 处修改已应用"

**预期结果：**

- ✅ 对话迭代使用流式传输
- ✅ 有明确的"增量修改"进度反馈
- ✅ 代码长度变化正确显示（如"代码从 3500 → 3800 字符"）

### 测试 3.2：Patch 失败回退的流式效果

**步骤：**

1. 输入一个故意难以 Patch 的修改："重写整个 CSS 部分，改用 Tailwind 风格的类名"
2. 观察：
   - Patch 应用可能失败（因为改动太大）
   - 应看到"增量修改未成功，回退到完整重写..."
   - 然后继续流式生成完整代码

**预期结果：**

- ✅ Patch 失败时优雅回退
- ✅ 回退过程有明确提示
- ✅ 最终仍能生成正确结果

## 四、多 Agent 执行效果测试

> 对应已修复：PR #26 生成阶段异步代码摘要 + PR #31 approve 挂起门持久化

### 测试 4.1：Agent 间通信（Memory 共享）

**步骤：**

1. 输入："做一个番茄钟应用，25 分钟工作、5 分钟休息，要有进度环动画"
2. 观察执行日志（ExplainabilityPanel）：
   - clarify Agent（产品经理）→ 输出需求摘要
   - spec Agent（架构师）→ 基于 clarify 输出设计规格
   - generate Agent（工程师）→ 基于 spec 生成代码
   - verify Agent（审查员）→ 检查代码质量
3. 确认各 Agent 的输入输出在日志中有正确关联

**预期结果：**

- ✅ 各 Agent 的角色名称正确显示
- ✅ Agent 间通过 Topic 正确传递上下文
- ✅ 执行日志完整可追溯

### 测试 4.2：实时进度事件序列

**步骤：**

1. 打开浏览器 DevTools → Network → 找到 SSE 连接
2. 输入需求并生成
3. **观察 SSE 事件流**：
   - `start` 事件（含 SOP 信息）
   - `agent_event` 系列：
     - `agent:start`（clarify、spec、generate...）
     - `agent:thinking`（生成子步骤，如"正在生成 CSS 样式"）
     - `agent:progress`（字符数/百分比更新）
     - `agent:summary`（异步代码摘要，如"正在实现倒计时逻辑"）
     - `file:generated`（文件生成完成）
     - `agent:complete`（阶段完成）
   - `approve_needed`（如适用）
   - `project_created`/`project_updated`（持久化事件）
   - `done`（最终完成）

**预期结果：**

- ✅ 事件序列完整，无遗漏
- ✅ agent:summary 在 generate 阶段至少出现 1 次
- ✅ progress 事件频率合理（不 spam 也不稀疏）

## 五、边界情况和异常处理测试

### 测试 5.1：need_clarification 软着陆

**步骤：**

1. 输入一个极其模糊的需求："做个东西"
2. 观察 clarify 阶段：
   - 应返回 `status: "need_clarification"`
   - 前端状态变为 "need_input"（不是 failed）
   - 显示问题清单（如"你想做网页还是 App？"）
3. 在输入框回答澄清问题
4. 观察流程继续

**预期结果：**

- ✅ 不直接失败，而是软着陆暂停
- ✅ 问题清单清晰可读
- ✅ 补充信息后流程继续，不丢失上下文

### 测试 5.2：规格拒绝后重新发起

**步骤：**

1. 输入需求并走到 approve 阶段
2. 点击「拒绝规格」
3. 观察：
   - 版本状态变为 failed
   - 显示"规格被拒绝，请重新描述需求"
4. 重新输入修改后的需求
5. 确认新走一遍完整流程

**预期结果：**

- ✅ 拒绝后正确标记失败状态
- ✅ 可以重新发起，不卡住

### 测试 5.3：免费账号权限控制

**步骤：**

1. 注册/登录一个免费账号（或使用 free@mini-atoms.demo）
2. 输入需求点击生成
3. 观察：
   - 应返回 403
   - 显示"免费账号仅支持体验示例项目，AI 生成需付费账号"

**预期结果：**

- ✅ 免费账号被正确拦截
- ✅ 错误提示清晰

### 测试 5.4：未登录状态

**步骤：**

1. 清除 cookie / 使用无痕模式不登录
2. 首页输入需求
3. 观察：
   - 应提示"请先登录后再使用生成"
   - 或直接跳转登录页

**预期结果：**

- ✅ 未登录用户被正确引导

## 八、快速回归测试（每次代码修改后执行）

如果没时间跑完整测试，至少验证这 3 个核心路径：

1. **新项目生成**：首页输入 → 完成生成 → 右侧有预览 ✅
2. **同一项目修改**：在项目内输入修改 → 生成 v2 → v2 基于 v1 ✅
3. **刷新恢复**：生成过程中刷新 → 恢复状态 → 最终完成 ✅

这三个全部通过 = 面试官反馈的核心问题已解决。

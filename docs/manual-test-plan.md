# mini-atoms 手动测试 SOP

> 手动测试是自动化 E2E 的互补层：机器断言"流程和数据对不对"，人判断"体验对不对"。
> 本文档把手动测试流程化：**什么时候跑、按什么顺序跑、每条看什么、怎么判定、怎么记录**。

---

## 〇、两层测试分工（先读这个）

| 层     | 工具               | 覆盖                                            | 不能覆盖                               |
| ------ | ------------------ | ----------------------------------------------- | -------------------------------------- |
| 自动化 | `npm run test:e2e` | SOP 路由、确认门、版本链、DB 落库、产物过校验层 | 卡住感知、UI 引导、视觉/交互、文案情绪 |
| 手动   | 本文档             | 只有人能判断的体验维度                          | （全部）                               |

**执行顺序**：先跑自动化 E2E（全绿）→ 再跑手动。自动化挂了就不用动手了，先修。

**执行时机**：

- **面试/发版前**：自动化 E2E + 手动全量（约 30-40 分钟）
- **每次代码修改后**：自动化 E2E + 手动快速回归（第八节，5 分钟）

**通过门槛**：

- P0 用例（标注 🔴）全部通过 = 可以面试/发版
- P1 用例失败 → 记入「已知问题」并附规避说明，可以演示但需主动披露
- P2 用例失败 → 记录即可

---

## 一、测试环境准备（2 分钟）

1. 浏览器**无痕模式**（避免缓存干扰）
2. 确认目标环境：
   - 本地：`npm run dev` → http://localhost:3000
   - 线上：https://mini-atoms-five.vercel.app/
3. 登录付费账号（免费账号配额为 0，跑不了生成）
4. 打开 DevTools → Network 面板（观察 SSE 用，保持常开）
5. 准备计时工具（手机秒表即可，量化"卡住感知"）

**记录起点**：在测试记录表（第七节）填写日期、环境、账号、 commit 版本（`git log --oneline -1`）。

## 二、创建流程（P0 🔴）

> 自动化 E2E 已覆盖路由/确认门/落库正确性；手动重点是**阶段卡片的引导感和卡住感知**。

### 用例 2.1：基础网页应用（web-app SOP，含确认门）🔴

**输入**：`做一个待办清单应用，可以添加、删除、标记完成，数据本地保存`

**步骤与观察点**：

1. 首页输入框提交 → 自动进入工作区
2. 阶段卡片依次激活：需求澄清 → 规格生成 → **规格确认（弹出三段式 SpecCard）**
3. 在 SpecCard 点击「确认」
4. 代码生成阶段观察：
   - ⏱ **卡住感知**：任何阶段超过 15 秒无任何反馈变化即记为观感失败
   - 应有字符数进度、子步骤提示（"正在生成 CSS 样式"等）、异步代码摘要
5. 完成后右侧 PreviewFrame 渲染待办应用
6. **实际操作预览**：添加一条任务、勾选完成、删除——三个交互都要真的能用

**预期**：

- ✅ 确认门正常弹出且按钮可用
- ✅ 全程无"死屏"感（最长静默 < 15 秒）
- ✅ 预览应用三个交互真实可用
- ✅ 版本卡片显示 v1，标题带 SOP 名（【网页应用】）

### 用例 2.2：复杂应用（fullstack-app 多阶段 SOP）

**输入**：`做一个带用户登录功能的博客系统，有文章列表、文章详情、评论功能，用 localStorage 模拟数据库`

**观察点**：

1. 路由到【全栈应用】，阶段卡片包含：数据层生成/校验 → 骨架生成/校验 → 页面生成/校验 → 合并整合 → 校验
2. 每个子阶段有独立进度反馈
3. 合并整合是系统动作（秒级完成，无 LLM 等待）
4. 预览实际可用（能切换页面、发评论）

**预期**：✅ 多阶段流转清晰可辨；✅ 最终应用功能完整

### 用例 2.3：小游戏（game SOP，无确认门直通）🔴

**输入**：`做一个 2048 游戏，要有动画效果和分数统计`

**观察点**：规格生成后**不出现**确认门，直接进代码生成；生成完即可玩。

**预期**：✅ 无确认门；✅ 游戏真的可以玩（方向键操作有响应、分数会动）

### 用例 2.4：长生成压力（卡住感知专项）🔴

**输入**：`做一个模拟城市建设游戏，有资源管理、建筑升级、人口系统、昼夜循环、天气系统，界面要精美`

**观察点**：

1. 全程计时：从提交到 done 的总时长
2. 生成阶段超过 60 秒时，进度反馈是否仍在更新
3. 若触发修复循环：应看到"校验未通过，自动修复重试（第 N 次）"
4. Network 面板确认 SSE 连接不断（心跳每 15 秒）

**预期**：

- ✅ 全程无超过 15 秒的反馈静默
- ✅ 修复循环有明确轮次提示
- ✅ 记录总时长到测试记录（用于跨版本对比退化）

## 三、修改流程（modify SOP，P0 🔴）

> 对应面试官反馈"修改产物应是版本迭代而非独立项目"。
> 自动化已覆盖版本链正确性；手动重点是**修改过程的透明度和 diff 摘要**。

### 用例 3.1：基础修改 + 版本链 🔴

**前置**：完成用例 2.1（待办应用 v1）

**步骤**：

1. 底部输入框输入：`把页面改成深色模式`
2. 观察阶段卡片走 modify SOP：**改动定位 → 补丁生成 → 补丁应用 → 校验**
   - 改动定位（架构师）：应显示"定位到 N 个改动点"
   - 补丁生成（工程师）：应有字符进度（补丁是小输出，进度跳动比全量生成快）
   - 补丁应用（系统）：**显示 diff 摘要**（改了哪几处、什么内容）
3. 完成后：
   - 版本列表出现 **v2，标注"基于 v1"**
   - 预览切换为深色模式
4. 点击 v1 卡片 → 预览切回浅色；点击 v2 → 深色。**版本可自由切换**

**预期**：

- ✅ v2 追加在同一项目（Sidebar 项目数不增加）
- ✅ diff 摘要准确描述了实际改动
- ✅ 版本切换预览正确

### 用例 3.2：从旧版本分叉 🔴

**步骤**：

1. 选中 **v1**（浅色版）
2. 输入：`添加按已完成/未完成筛选的功能`
3. 观察新版本 **v3 标注"基于 v1"**（不是 v2）
4. v3 应是浅色背景 + 筛选功能（继承 v1 而非 v2）

**预期**：✅ 分叉基准正确；✅ UI 明确显示"基于 vN"

### 用例 3.3：修改失败的安全行为

**步骤**：

1. 输入一个含糊的修改：`优化一下代码`
2. 可能出现：定位不到明确改动点 → 补丁重试 → 次数用尽后 **fail**
3. 观察失败态：**旧版本产物必须完好保留**，预览不变成空白/半成品

**预期**：✅ 失败有明确文案；✅ 旧版本不受损

## 四、恢复流程（P0 🔴）

> 刷新是面试官最爱干的事。

### 用例 4.1：确认门挂起时刷新 🔴

**步骤**：

1. 新建项目，走到规格确认门（SpecCard 弹出）
2. **F5 刷新**
3. 应自动恢复"规格待确认"卡片（规格内容完好）
4. 点击「确认」→ 流水线继续（同进程 live）或给出清晰的重发提示（服务已重启 recorded）

**预期**：✅ 恢复卡片规格完好；✅ 两种结局都有明确引导，无死等

### 用例 4.2：生成中途刷新 🔴

**步骤**：

1. 新建项目，确认规格后进入代码生成
2. 生成进行中 **F5**
3. 从 Sidebar 重新进入该项目
4. 观察：显示"后台生成中…（完成后自动刷新）"，前端每 5 秒轮询，新版本落库后自动重建工作区
5. 过程数据（阶段状态、执行日志）应完整回放，不是一片空白

**预期**：✅ 轮询恢复生效；✅ 过程数据完整保留

## 五、异常与边界（P1）

### 用例 5.1：模糊需求软着陆

**输入**：`做个东西`

**预期**：不判负——状态为"待补充"，列出模型的引导问题清单；在输入框补充描述后流程继续（原需求+补充合并提交）。

> 注：模型是否要求澄清是非确定行为。若它直接给了规格，走用例 5.2 拒绝路径即可，不记失败。

### 用例 5.2：规格拒绝

**步骤**：确认门点「修改」→ 版本标记失败 + "规格被拒绝，请重新描述需求" → 重新输入可再次发起。

**预期**：✅ 不卡死；✅ 文案无技术黑话

### 用例 5.3：权限边界

1. 免费账号生成 → 403 + "免费账号仅支持体验示例项目"
2. 未登录访问 → 引导登录

**预期**：✅ 拦截正确，文案清晰

### 用例 5.4：罐头演示（零成本路径）

Sidebar 打开示例项目（待办/贪吃蛇/计时器）→ 秒开、可交互、不走 LLM。

**预期**：✅ 离线演示可用的兜底路径完好

## 六、体验专项（P1，机器测不了的部分)

### 用例 6.1：执行日志可读性

**步骤**：任意生成过程中阅读「Agent 执行队列」面板。

**预期**：

- ✅ 角色名是中文业务语言（产品经理/架构师/前端工程师/代码审查员）
- ✅ 日志能回答"现在谁在干什么、进行到哪了"
- ✅ 无英文技术术语直接外泄（如 SSE、JSON、500）

### 用例 6.2：错误文案情绪核对

故意触发一次失败（如断网后操作），阅读所有红色/失败文案。

**预期**：✅ 文案告诉用户"发生了什么 + 接下来怎么办"，无 raw JSON/堆栈外泄

### 用例 6.3：预览与下载

**预期**：✅ iframe 内应用可完整交互（sandbox 不破坏功能）；✅ 版本切换即点即换；✅ 如有下载入口，下载的 HTML 文件双击可直接运行

## 八、快速回归（每次代码修改后，5 分钟）

完整手动测试的全量子集，三条核心路径：

1. 🔴 **新建**：首页输入 → 确认门 → 生成完成 → 预览可交互
2. 🔴 **修改**：项目内输入修改 → v2 基于 v1 → 版本可切换
3. 🔴 **刷新**：生成中途 F5 → 恢复/轮询 → 最终完成

三条全过 = 核心链路无回归。配合 `npm run test:e2e` 即为完整闸门。
